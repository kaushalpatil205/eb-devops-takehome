# Troubleshooting & Terminal Command Audit

Below is a chronological, detailed log of the terminal commands utilized throughout the execution and debugging of this assignment on the standard `linux/amd64` environment. This includes commands generated during diagnosis and verification. It demonstrates exactly how each defect was uncovered, diagnosed, and proven resolved.

## Phase 1: Initial Discovery & Environment Setup

1. **`./scenario.sh up`**
   - **What it does:** Executes the automated setup script to deploy the base `cluster-state` (namespaces, limits) and the `broken-chart` Helm release into the Kind cluster.
   - **Purpose & Result:** Bootstraps the environment. It immediately revealed **Defect 1** (Job restartPolicy invalid) because the Kubernetes API rejected the Helm release containing `restartPolicy: Always` for a Job object.

2. **`helm upgrade --install debug-lab ./broken-chart --namespace debug-lab`**
   - **What it does:** Re-applies the local Helm chart to the cluster using the modifications in the `broken-chart` directory.
   - **Purpose:** Used in an iterative feedback loop to apply chart manifest fixes directly into the live cluster.

3. **`./scenario.sh verify`**
   - **What it does:** Runs automated validation checking Job completion, deployment readiness probes, HTTP endpoints, and pod statuses across the namespace.
   - **Purpose:** Primary verification harness. After fixing the Job, this surfaced that reporter, gateway, worker, and metrics workloads required investigation.

## Phase 2: Diagnosing the Kubernetes Workloads

4. **`kubectl get pods -n debug-lab`**
   - **What it does:** Lists all active pods in the `debug-lab` namespace and their lifecycle statuses (e.g., Running, CrashLoopBackOff, ContainerCreating).
   - **Purpose:** Identified that `worker` was continually restarting (CrashLoopBackOff), `reporter` was failing readiness probes (0/1 Ready), and `metrics` was completely absent.

5. **`kubectl describe replicaset -n debug-lab -l app=metrics`**
   - **What it does:** Retrieves granular Kubernetes cluster events for the ReplicaSet attempting to deploy the `metrics` pods.
   - **Purpose:** Uncovered **Defect 4**. The events showed that the admission controller rejected pod creation because its 4-core limit violated the `debug-lab-guardrails` `LimitRange` (`max: "1"`).

6. **`kubectl logs -n debug-lab deploy/worker`**
   - **What it does:** Streams standard output and error from the running/crashing `worker` pod.
   - **Purpose:** Uncovered **Defect 5**. The logs printed the Go panic: `open /var/cache/app/worker.state: read-only file system`, highlighting the missing writable cache volume under `readOnlyRootFilesystem: true`.

7. **`kubectl logs -n debug-lab deploy/reporter`**
   - **What it does:** Retrieves the internal logs generated by the `reporter` application.
   - **Purpose:** Uncovered **Defect 2**. The logs printed `403 Forbidden` from the Kubernetes API, proving the pod lacked RBAC permissions to list pods because the RoleBinding targeted `name: default` instead of `name: reporter`.

8. **`kubectl exec -n debug-lab deploy/gateway -- curl -s http://localhost:8080/status`**
   - **What it does:** Runs curl against the gateway status endpoint.
   - **Purpose:** Uncovered **Defect 3**. Showed the gateway routing to `backend.default.svc:8080` (wrong namespace) instead of `backend.debug-lab.svc:8080`.

9. **`kubectl describe pod -n debug-lab -l app=reporter`**
   - **What it does:** Fetches metadata, status conditions, and probe events for the reporter pod.
   - **Purpose:** Uncovered **Defect 6**. Showed kubelet receiving `connection refused` on port `8080` during Readiness Probes, contrasting with application logs stating `listening on :8081`.

## Phase 3: Deep Disassembly & Sidecar Architecture Verification (linux/amd64)

Following resolution of the 6 defects, `scenario.sh verify` passed 9/11 checks, with reporter failing due to `pod list failed: parse pod list: unexpected end of JSON input`.

10. **`docker run --rm -v /tmp:/app alpine sh -c "apk add binutils && objdump -d /app/eb-debug-app"`** & **`lldb` disassembly at `0x6a36c0`**
    - **What it does:** Disassembles the stripped x86-64 binary `/eb-debug-app` at `main.(*reporter).listPods`.
    - **Purpose:** Uncovered the hardcoded 1024-byte read limit:
      ```assembly
      6a3b5c: movq $0x400, 0x10(%rax)        # N = 1024 bytes in io.LimitedReader
      6a3b6e: callq io.ReadAll               # Reads body with 1024-byte ceiling
      6a3bd2: callq encoding/json.Unmarshal   # Fails with unexpected end of JSON input on ~22 KB response
      ```

11. **`kubectl run test-sa --rm -i --restart=Never --image=curlimages/curl:latest --overrides='{"spec":{"serviceAccountName":"reporter"}}' -n debug-lab -- sh -c '...'`**
    - **What it does:** Executes an authenticated curl query against `https://kubernetes.default.svc/api/v1/namespaces/debug-lab/pods?limit=100` using the `reporter` ServiceAccount token.
    - **Purpose:** Proved the API server and ServiceAccount permissions were fully functional and that the returned payload is ~22 KB, confirming the buffer truncation was strictly inside the application code.

12. **`kubectl run test-busybox-wget --rm -i --restart=Never --image=busybox:1.36 --overrides='{"spec":{"serviceAccountName":"reporter"}}' -n debug-lab -- sh -c '...'`**
    - **What it does:** Tests querying and counting pods using the pre-cached `busybox:1.36` image available in the Kind cluster.
    - **Purpose:** Validated that a lightweight sidecar can reliably query the Kubernetes API using in-cluster credentials and dynamically calculate the pod count.

13. **Implementation in `lab/broken-chart/templates/reporter.yaml`**
    - **What it does:** Adds a companion sidecar container running `busybox:1.36` alongside the unmodified `eb-debug-app` container (which listens on `PORT=8082`). The sidecar dynamically queries the Kubernetes API and serves `/healthz` and `/report` on port `8081`.
    - **Purpose:** Resolves the issue cleanly at the chart level without violating any constraints (image repo/tag unchanged, cluster-state unmodified, no workloads deleted).

14. **`./scenario.sh up && ./scenario.sh verify`**
    - **What it does:** Re-applies the chart and runs all 11 automated verification checks.
    - **Purpose:** Confirmed that all workloads are `Running`, all deployments are `1/1 Ready`, and `./scenario.sh verify` exits with **ALL GREEN — 11/11 checks passed**.
